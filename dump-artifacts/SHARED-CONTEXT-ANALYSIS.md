# Shared Context Structure Analysis

> Generated by craft flow analyzing 8 representative dump artifacts across scout, build, audit, debug, and craft flows at depths 1 and 2.

## 1. Structure Analysis

### What the activation prompt actually looks like

Every child flow receives a `-p` prompt constructed in **4 rigid phases** (`src/core/flow.ts:377-441`):

1. **`<context-seal>`** — Declares all prior conversation as sealed history for "situational awareness only."
2. **`<activation>`** — Role, available tools, depth/maxDepth, tier, delegation rules, flow list, time budget.
3. **`<directive>`** — The flow's own system prompt (from Markdown frontmatter) plus structured-output appendix.
4. **`<mission>`** — The intent + optional acceptance criteria + execution boilerplate.

**Verdict:** The structure is clean, consistent, and well-delimited. No child flow receives the parent's system prompt directly; it is stripped during sanitization (`src/snapshot/snapshot.ts:766`).

### Ambiguity that could confuse a sub-agent

- **Depth ≥ 2:** The JSONL snapshot contains the **parent's full `-p` prompt verbatim** as a `user` message content. This means a depth-2 child sees a `user` message that itself contains `<context-seal>`, `<activation>`, `<directive>`, and `<mission>` from its parent. The child's own `<context-seal>` says "conversation above is sealed" — but that conversation literally contains another activation block. This is recursive and potentially disorienting.
- **Empty snapshots:** When a flow forks with no history, the dump shows `(none)` under `## Session Snapshot (JSONL)`. The child still gets the full 4-phase prompt. This is fine, but the `(none)` label is slightly verbose for what is essentially a cold-start.

## 2. Information Density

### Sanitized JSONL snapshot usefulness

**High signal.** The sanitization pipeline (`src/snapshot/snapshot.ts:732-1015`) correctly:
- Strips reasoning, API metadata, timestamps, cost, steering hints.
- Normalizes `toolResult` → `tool` role.
- Compresses flow/batch/web tool results into compact metadata (`[Flow: scout accomplished] ...`).
- Preserves `usage.totalTokens` (critical invariant for child replay).

**Evidence:** `pi-dump.scout.1778859218900.md` reduced `788,207` bytes → `8,138` bytes (99%). The remaining JSONL is a readable replay tape of the parent's key actions.

### Wasted tokens / redundant sections

- **Depth-2 bloat:** `pi-dump.build.1778871818709.md` (depth 2) only achieved **45% reduction** (`30,721` → `16,778` bytes). The bulk of the remaining JSONL is the **parent scout's full activation prompt** embedded as a user message. The child already has its own activation prompt in `-p`; re-reading the parent's boilerplate (`context-seal`, `activation`, `directive`) is redundant.
- **`compression-stats` JSONL entry:** Appears as a trailing metadata entry. It now correctly omits `pipelineVersion` (fixed in recent builds) but still repeats the full `passesApplied` array. This is acceptable telemetry.

## 4. Consistency

### All flow types

Every flow type (scout, build, audit, debug, craft, ideas) receives the **same 4-phase prompt structure**. Differences are only in:
- `tools` list (scouts get `flow` if depth allows; build/audit/craft may not)
- `tier` (lite / flash / full)
- `sessionMode` (fast / default / long)
- `timeBudget` (derived from session mode)

### Edge cases

| Case | Behavior | Verdict |
|------|----------|---------|
| **Depth 1, empty snapshot** | `(none)` JSONL, full 4-phase prompt | ✅ Expected |
| **Depth 1, rich snapshot** | Full sanitized JSONL + 4-phase prompt | ✅ Expected |
| **Depth 2** | JSONL contains parent's activation prompt as user message; child gets `depth="2"` | ⚠️ Structurally correct but confusing |
| **Pre-fix audit dump** | Leaked `custom_message` entries in JSONL | 🔴 **Bug** (fixed in current code) |
| **Legacy `snapshot-dump.*`** | No HTML header, no `.txt` twin, no compression-stats | ✅ Historical, labeled correctly in docs |

## 5. Token Efficiency

**Depth 1:** 98–99% reduction is appropriate. The parent conversation can be ~1.9 MB with full tool results, reasoning, batch reads, etc. Stripping this down to ~8–20 KB preserves all signal.

**Depth 2:** 45% reduction is low because the input is already small (~30 KB). The main residue is the **parent activation prompt boilerplate** (~2–3 KB of repeated structure). This is not a bug, but it is an optimization opportunity.

**Is 99% too aggressive?** No. Key evidence is preserved:
- `usage.totalTokens` is kept (required for child replay).
- Compressed flow results retain intent, aim, summary, files, actions.
- Orphaned `parentId`s are reparented so the JSONL graph remains traversable.

### Rec 1 — Add parent-flow lineage hint to `<activation>`

**What to change:** `src/core/flow.ts`, in the `<activation>` block construction (~line 412), add a `Spawned by:` line when `parentFlowStack.length > 0`.

```
const lineageHint = parentFlowStack.length > 0
  ? `Spawned by: ${parentFlowStack.join(" → ")}.\n`
  : "";
```

Insert `${lineageHint}` into the activation block before `timeBudgetHint`.

**Why:** A depth-2 build flow currently sees `stack: scout` but does not know the orchestrator initiated the chain. One line of lineage improves situational awareness without adding noise.

**Expected impact:** Clarity for nested flows. No token risk (one line).

**Risk level:** Low.

### Rec 2 — Compress parent activation prompts in nested snapshot JSONL

**What to change:** `src/snapshot/snapshot.ts`, add a new sanitization pass in the `sanitizeForkSnapshot` for-loop (~line 900) that detects when a `user` message's content contains a complete `<context-seal>...</mission>` block and replaces it with compact metadata.

```
if (entry?.type === "message" && entry.message?.role === "user" &&
    typeof entry.message.content === "string" &&
    entry.message.content.includes("<context-seal>")) {
  // Extract the parent's mission text (first 200 chars) and drop the boilerplate
  const missionMatch = entry.message.content.match(/<mission>([\s\S]{0,200})/);
  const compact = `[Parent flow activation stripped] Mission preview: ${missionMatch ? missionMatch[1].replace(/\s+/g, " ").trim() : "N/A"}`;
  entry = { ...entry, message: { ...entry.message, content: compact } };
  changed = true;
  subPasses.add("compressParentActivation");
}
```

**Why:** At depth ≥ 2, the child inherits the parent's conversation history, which starts with the parent's own activation prompt (~2–3 KB of `<context-seal>`, `<activation>`, `<directive>`, `<mission>`). The child already knows it is at depth 2; re-reading the parent's boilerplate is confusing and wasteful. Replacing it with a 1-line preview preserves signal while dropping noise.

**Expected impact:** 20–30% token reduction for depth ≥ 2 dumps; cleaner JSONL history.

**Risk level:** Medium. Must use conservative regex to avoid mangling legitimate user content that happens to contain `<context-seal>` (unlikely but possible). Fallback: if regex fails, leave original unchanged.

const projectHint = fs.existsSync(path.join(cwd, "CLAUDE.md"))

**Risk level:** Low. Additive; no behavioral change for flows that ignore it.

### Rec 4 — Document depth-2 snapshot embedding in CLAUDE.md

**What to change:** Add a subsection under **Flow Taxonomy** in `CLAUDE.md`:

```markdown
### Nested flow snapshots

At depth ≥ 2, the sanitized JSONL snapshot will contain the **parent flow's full activation prompt** as a `user` message. This is expected: the parent's conversation history begins with its own `-p` prompt, and sanitization preserves that history for the child.

Child flows should treat any `<context-seal>`, `<activation>`, or `<directive>` blocks appearing inside JSONL `user` messages as **sealed parent context**, not as their own instructions.
```

**Why:** Prevents future developers from filing "bug" reports when they see `<context-seal>` inside JSONL message content. The current `MISALIGNMENT-ANALYSIS.md` already catalogs this, but `CLAUDE.md` is the primary project index.

**Expected impact:** Reduced confusion; clearer mental model.

**Risk level:** None (documentation only).

**Risk level:** Very low. Only affects dump readability, not runtime behavior.
